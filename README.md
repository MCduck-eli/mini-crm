# Mini-CRM «Объекты и задачи»

Лёгкая CRM для строительной компании: учёт объектов, постановка задач исполнителям и строгий журнал статусов. Интерфейс на русском, права разграничены на уровне базы данных.

## Возможности

- Две роли: **Постановщик** (`manager`) и **Исполнитель** (`worker`).
- Объекты: постановщик создаёт и редактирует все; исполнитель видит только те, по которым у него есть задача.
- Задачи: назначаются исполнителю и объекту, живут по фиксированному циклу статусов.
- История: каждое изменение статуса автоматически пишется в неизменяемый журнал с автором, временем и комментарием.
- Отдельная страница «Мои задачи» для исполнителя.

## Локальный запуск

```bash

# создать .env.local вручную (в файле две строки — см. раздел «Переменные окружения»)
```


## Переменные окружения

| Имя | Значение |
| --- | --- |
| `VITE_SUPABASE_URL` | Project URL из Supabase → Settings → API |
| `VITE_SUPABASE_ANON_KEY` | Ключ `anon public` / publishable key |

Префикс `VITE_` обязателен: Vite подставляет такие переменные в клиентский код на этапе сборки. **Эти значения публичны** — безопасность держится на RLS, а не на скрытии ключа. `service_role` во фронтенд не должен попадать ни при каких условиях.

## Настройка Supabase

Выполнять строго по порядку, целиком одним запуском в SQL Editor (каждый файл написан «paste-safe»: долларовые теги `$fn$`/`$do$`, сигнатуры функций в одну строку, пустых строк внутри операторов нет).

1. `supabase/schema.sql` — таблицы, роли, триггеры, RLS, RPC `change_task_status`, функция `admin_create_user`.
2. `supabase/seed.sql` — демо-объекты, задачи, история и демо-аккаунты.
3. `supabase/patch-history-cascade.sql` — обновляет триггер `protect_task_history`, чтобы удаление объекта или задачи каскадом снимало и журнал (в ТЗ постановщик имеет право удалять задачи и объекты). В конце файл сам себя проверяет и печатает `OK 1 / OK 2 / OK 3`.
4. По желанию: `supabase/add-second-executor.sql` — создаёт второго исполнителя и три его задачи (см. «Демо-доступы»).
5. При проблемах со входом — `fix-demo-logins.sql`, затем `fix-demo-auth-metadata.sql`.

Обязательно после настройки проекта:

- **Authentication → Sign In / Up → Email**: выключить «Allow new users to sign up» (регистрация закрыта, аккаунты создаёт постановщик через `admin_create_user` или Dashboard).
- Новые сотрудники создаются постановщиком: либо через Dashboard (Authentication → Users → Add user, с флагом «Auto Confirm User»), либо функцией `admin_create_user` в SQL Editor. Самостоятельная регистрация закрыта.

## Демо-доступы

| Роль | Email | Пароль |
| --- | --- | --- |
| Постановщик | `boss@stroyka.ru` | `manager123` |
| Исполнитель | `builder1@stroyka.ru` | `worker123` |
| Исполнитель | `builder2@stroyka.ru` | `worker123` |

`builder2@stroyka.ru` появляется так: Dashboard → Authentication → Users → **Add user** (email `builder2@stroyka.ru`, пароль `worker123`, включить «Auto Confirm User»), затем целиком выполнить `supabase/add-second-executor.sql`. Скрипт даёт ему три задачи в разных статусах и повторяет записи журнала; повторный запуск дублей не создаёт.

Legacy-аккаунты `manager@stroyka.ru`, `worker1@stroyka.ru`, `worker2@stroyka.ru` созданы функцией `admin_create_user`, но GoTrue их не пускает (нет корректных записей `auth.identities`) — оставлены как есть, не удалять: их задачи и история уйдут каскадом.

## Бизнес-правила

Цикл статусов:

```
Новая → В работе → На проверке → Принята
                              ↘ На доработке → В работе (по кругу)
```

| Кто | Может |
| --- | --- |
| Постановщик | создавать объекты и задачи, редактировать, удалять, принимать работу (`Принята`) и отправлять на доработку (обязателен комментарий) |
| Исполнитель | видеть только свои задачи и объекты по ним, менять **только статус**: `Новая`/`На доработке` → `В работе`, `В работе` → `На проверке` |

`title`, `description`, `object_id`, `assignee_id`, `author_id` исполнитель изменить не может — это проверяется триггером `validate_task_update`, а не только скрытием кнопок в интерфейсе.

## Как обеспечивается безопасность

- **RLS включён на всех четырёх таблицах**; роль берётся из `public.profiles.role` (JWT `app_metadata.role` — только запасной путь, подделка claim не даёт прав).
- Политики: `objects_manager_all`, `objects_worker_select`, `tasks_manager_all`, `tasks_worker_select`, `tasks_worker_update`, `history_select_participants`, `history_no_client_insert`.
- Смена статуса идёт **только** через `security definer` RPC `change_task_status`, который вызывает те же бизнес-триггеры и пишет запись в историю.
- `task_history` защищён от UPDATE и DELETE триггером `protect_task_history`: прямая правка или чистка журнала из API невозможна ни для какой роли. Исключение сделано только для каскада, который запускает сам сервер при удалении задачи или объекта постановщиком (`pg_trigger_depth() > 1`) — иначе ТЗ противоречило бы само себе: постановщик имеет право удалять задачи, но почти у всех задач уже есть история.
- `admin_create_user` не исполняется ни `anon`, ни `authenticated` из клиента.
- Удаление объекта каскадно удаляет его задачи и их журнал — это осознанное поведение, проверка «есть ли история» больше не блокирует удаление.

## Деплой на Vercel

1. Залить репозиторий на GitHub/GitLab.
2. Vercel → **Add New → Project** → выбрать репозиторий.
3. Framework Preset: `Vite`. Build Command `npm run build`, Output Directory `dist` — подхватываются автоматически, `vercel.json` отвечает за SPA-rewrites.
4. Environment Variables для окружения Production: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`.
5. Deploy. После сборки проверить вход, список объектов и смену статуса.
6. Если для проекта включены дополнительные ограничения доступа к API (allowlist по домену) — добавить домен Vercel. По умолчанию Supabase принимает запросы с любого origin, это штатная схема для публичного anon-ключа.

Ключи меняются через Vercel → Settings → Environment Variables и повторный деплой; в `.env.local` их коммитить нельзя (уже в `.gitignore`).

## Решения и допущения

- **Роль живёт в `public.profiles`, а не в JWT.** Claim `app_metadata.role` читается только как запасной вариант, если профиля нет: подделать его нельзя, права считаются из таблицы.
- **Права проверяются триггерами + RLS.** RLS решает «какие строки видно», BEFORE-триггеры — «разрешён ли такой переход вообще». Поэтому прямой `PATCH /rest/v1/tasks` с неверным статусом отбивается так же, как кнопка в интерфейсе.
- **Комментарий к смене статуса передаётся через транзакционную настройку** `app.task_action_comment`, а не как аргумент триггера: PostgREST не умеет передавать служебные поля в `UPDATE`. Настройка имеет `local` область, то есть живёт ровно одну транзакцию и не «протекает» между запросами.
- **Смена статуса — только RPC** `change_task_status`: она атомарно обновляет задачу и пишет журнал, так что запись истории не может существовать без смены статуса и наоборот.
- **Демо-аккаунты заведены через Dashboard, а не `admin_create_user`.** Функция писала `auth.identities` в колонку `auth_user_id`, а в реальном Supabase она называется `user_id`; ошибка проглатывалась `exception when others then null`, и GoTrue не пускал таких пользователей. Теперь колонка определяется динамически, но рабочие аккаунты в демо — созданные вручную.
- **`builder2@stroyka.ru` заводится отдельным скриптом**, потому что пароль пользовательского аккаунта из SQL задать надёжнее всего через Dashboard, а роли и задачи дописывает `add-second-executor.sql`.
- **Удаление объекта удаляет и его задачи, и их журнал** (каскад). Альтернатива «запретить удаление, если есть история» ломала бы пункт ТЗ про права постановщика, поэтому выбран каскад с точечным исключением в триггере.
- **Дизайн-допущение:** компании достаточно двух ролей и одного набора статусов из ТЗ; поля объекта — только название и адрес, у задачи — название, описание, объект, исполнитель, автор и статус.
- **Что не сделано:** вложения и фото, уведомления о смене статуса, пагинация и поиск по больш объёму, подрoli/команды объектов, экспорт в Excel, мобильная нативная версия, тесты в CI, мультиязычность, аудит действий кроме журнала статусов.
- **Тесты:** схема и RLS прогнаны на локальном PostgreSQL 15 с заглушкой `auth` по форме Supabase — 38 проверок (видимость строк, переходы статусов, права на изменение полей, прямые запросы в журнал). Живой проект проверял вход, списки и смену статуса вручную.

## Ограничения текущей версии

- Один уровень прав: две роли, без подролей и группировки по объектным командам.
- Нет вложений, фото и файлов по задаче.
- Нет уведомлений о смене статуса (email/push).
- Нет пагинации: списки задач загружаются целиком.
- Удаление объекта каскадно удаляет его задачи и их историю — отменить уже удалённый журнал нельзя, это осознанное поведение `on delete cascade`.
- Журнал статусов не архивируется и не чистится; служебная настройка `app.allow_history_write` включается только вручную в SQL Editor и только для административной чистки.
